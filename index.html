Abstract. FlyRank's rule-based system for flagging declining content pages for editor review is only 40% precise in its top-50 recommendations, wasting 30 of every 50 weekly editor reviews on pages that were never a real priority. This paper asks whether a trained model, evaluated honestly on real production data, can beat that rule — and whether a page's reason for underperforming (genuine decay vs. a SERP-answered query vs. a fixable CTR problem) can be diagnosed alongside its rank. Using 9.8 million daily performance rows from FlyRank's pseudonymized internal warehouse (55 clients, 331,437 content items, Feb–Mar 2026), a Random Forest classifier was trained on prior-month signals to predict next-month improvement, validated with a client-grouped split to prevent memorization. The model reached Precision@50 = 0.820 versus the baseline's 0.400 — cutting wasted editor reviews from 60% to 18% per week, roughly 21 extra productive reviews out of 50 — while a diagnosis layer classified 10.5% of eligible pages as likely SERP-answered, a pattern the existing rule cannot distinguish from genuine decline at all. This is decision-support evidence for FlyRank's editorial triage workflow, not a causal claim and not a claim about Google's ranking algorithm.

01 — Introduction / Problem

Editors can review 50 pages a week. The current rule wastes 30 of them.

FlyRank manages tens of thousands of pages across dozens of clients, but a human editor can carefully review only about 50 pages a week. The existing rule-based flag — in_striking_distance & has_real_volume — decides which 50 pages an editor opens first. On real March 2026 warehouse data, that rule is only 40% precise in its own top 50: 30 of 50 recommended pages turn out not to be real priorities. Every one of those 30 reviews is a paid editor-hour spent on a page that was never the problem, while a genuinely declining page elsewhere goes unlooked-at for another week.

A second, separate failure sits underneath the first: even when the rule is right that a page needs attention, it gives no reason why. A page whose clicks fell because Google now answers the query directly on the results page (no click opportunity left to recover) looks identical to the rule as a page that is genuinely stale and needs a rewrite — but the fix for each is completely different, and rewriting the first wastes the same editor-hour a second time.

The decision this project improves: which pages an editor opens first, and what kind of fix they should expect before opening the page — not just whether to review a page, but why.

Deliberately excluded, and why:

  • trend_direction / trend_pct — these are the source of the existing rule's own label; using them as features would be circular.
  • Any FlyRank product-decision column (health_score, priority_score, action_type) — these encode a decision the current system already made; feeding them back in would just teach the model to copy that decision, not discover anything new.
  • GA4-derived engagement fields — only 4.2% of March rows have ga4_data_available IS TRUE, too sparse to trust as a feature this month.
  • Raw client names, domains, URLs, and search queries — never present in the release at all.

03 — Methodology

A forward-looking label, a client-grouped split, and a diagnosis layer

Target

Unlike the starter pipeline's same-window is_declining_label, the label here is a genuine future outcome: did a page's CTR or average position improve from February to March? Features come entirely from February; the label comes entirely from March.

Features

impressions, clicks, avg_position, in_striking_distance, has_real_volume

All five are knowable at the February decision point — no feature crosses into March.

Baseline

The existing FlyRank-style rule, encoded transparently with no fitted weights: score = impressions × (in_striking_distance AND has_real_volume), where striking distance is position 11–30 and real volume is ≥100 impressions.

Model

Logistic Regression, then Random Forest (200 trees) — the same method ladder the starter pipeline itself used, for a true apples-to-apples comparison against FlyRank's own reference result (0.240 → 0.740 on the 30k-row starter slice).

Validation design — the honest part

Primary: client-grouped split (28 train clients, 12 test clients, no overlap). Pages from the same client share hidden patterns — a random split would let the model memorize a client's template rather than learn a transferable pattern. A second, plain random split is reported alongside on purpose, not hidden, to show the size of the memorization gap grouping protects against.

Diagnosis layer

A four-category classifier reused from ML-03's diagnose() logic, remapped onto this notebook's Feb (prior) / March (last) structure:

CategoryRuleEditor action
genuine_declineimpressions AND clicks both fellrefresh_or_rewrite
likely_serp_answeredimpressions held/grew, clicks fellflag_for_human_review_only
ctr_fixableCTR < 0.3, position ≤ 20review_title_and_meta
stable_or_improvingnone of the aboveno_action
Named up front: likely_serp_answered's real-world justification — that an AI Overview or featured snippet intercepted the click — rests on external industry reporting, not on FlyRank's own query-level SERP-feature data. It is a proxy signature, not a confirmed cause, and this paper never claims otherwise.

04 — Results

0.400 → 0.820: the model more than doubles baseline precision

Precision@50 — baseline rule vs. random forest (client-grouped)

Same 130,969-row test population, same client-grouped split, same metric. Base rate (share of pages that genuinely improved) was 46.5% — well below both scores, confirming the model is finding real signal, not just guessing high.

The memorization gap — grouped split vs. naive random split

A plain random split lets pages from the same client appear in both train and test, so the model can memorize a client's template instead of learning a transferable pattern — the perfect 1.000 score is a warning sign, not a win. Reported here on purpose rather than hidden, per the project's leakage-hunting discipline.

05 — Limitations & honest framing

What this work cannot claim

  • Snapshot, not causal proof. This shows an observed association between February signals and March outcomes on one client-grouped split. It does not show that acting on a recommendation causes a page to improve — that needs an A/B test or another causal design this data alone cannot provide.
  • avg_position = 0 bug, found via error review, not fixed. Per the data dictionary, 0 means "no position data," not literal rank zero — but the current query never filters it before averaging, pulling sparse-data pages toward an artificially strong position. 303 rows in the final queue carry this risk. The three most confidently wrong predictions in error analysis all shared this exact issue.
  • Only 40 of 55 March clients appear in the final model (28 train + 12 test). Investigated directly: only 5 are explained by having zero February history at all; the remaining 10 were removed by the ≥10-impression March volume filter — a deliberate, named filtering choice, not a join bug.
  • GA4 engagement signal is unusable this month. Only 4.2% of March rows have ga4_data_available IS TRUE — far too sparse to trust as a feature without an explicit "not available" category.
  • The SERP-answered diagnosis is directional, not confirmed. No query-level SERP-feature data (whether an AI Overview fired) exists in this release — the pattern is a proxy signature backed by external industry reporting, never presented as proof.
  • The ≥10-impression March filter excludes pages that went fully silent. A page could "improve" by disappearing entirely from a declining trend into total silence — that would not register as improved here.

06 — Ranked recommendations

The action playbook

Every recommendation below carries a reason code so an editor can see why, not just that.

DiagnosisRecommended actionHuman-review requirement
genuine_declineRefresh or rewriteConfirm this isn't consolidation, seasonality, or noise before commissioning a rewrite
likely_serp_answeredFlag for review only — no rewriteNever auto-confirmed as SERP-cannibalized; treat as "needs human judgment," not a settled diagnosis
ctr_fixableReview title / meta descriptionConfirm avg_position ≠ 0 (no-data) before trusting the position signal
stable_or_improvingNo action — protect, don't touch—

What should never be automated

  1. Auto-publishing a rewrite from genuine_decline alone — a human must rule out consolidation, seasonality, and noise first.
  2. Auto-confirming likely_serp_answered as cannibalization — the evidence is external and directional, not FlyRank's own confirmed signal.
  3. Treating model_score as a guaranteed outcome — it is a validated, honest probability (Precision@50 = 0.820), not a promise.

Monitoring / retrain triggers

  • Re-run monthly at minimum — this is a fixed Feb→Mar snapshot and will report the same pages forever without a refresh.
  • Watch the diagnosis-share baseline (CTR-fixable 58.1% / stable 23.9% / SERP-answered 10.5% / decline 7.5%) — a sharp shift signals something platform-wide changed.
  • Retrain if Precision@50 on a fresh month drops meaningfully below ~0.820.
